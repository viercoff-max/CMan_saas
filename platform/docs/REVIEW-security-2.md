# Security review 2 (read-only): Supabase SaaS layer

Scope: `platform/` at `main` 70782bc (2026-11-19). It covers what was added since `docs/REVIEW-security.md`: the Supabase schema, RLS, grants and RPCs; the Supabase DataStore; Supabase Auth, sessions, roles and team; Storage; Telegram; branding; the Anthropic provider and AI caps; the platform admin screen; public pages; retention in Supabase mode; dependencies; git history; logging.

Method: I read the code and the SQL. I ran `npm run typecheck` (clean), `npm test` (51 files, 782 tests pass) and `npm audit` (0 vulnerabilities). I scanned `git log -p` for secrets, reporting counts only. For H1 I wrote one scratch repro test outside the repo. No repo file was changed except this report. No live Supabase or external API was called.

Threat model assumed: a public self-serve SaaS (`/signup` open) on Vercel and Supabase. Attackers can be anonymous Internet users, a self-registered tenant, or a malicious or careless member (agent or admin) of a tenant. **RLS and grants are a real boundary.** The app keeps the publishable key server-side, but Supabase treats that key as public: it is meant to be browser-safe and may ship later with a Realtime or browser client. A member can also read their own access token from their own browser. So anything the `authenticated` role may do through `/rest/v1` or `/storage/v1`, a member can do directly, outside the app's checks.

## Verified as solid

- **Tenant wrapper** (`src/lib/data/supabase/client.ts:89-109`). `scoped()` adds `tenant_id = <tid>` to every select, update and delete, stamps `tenant_id` on every insert and upsert, strips `tenant_id` from update patches, and forces `p_tenant` on RPCs. Every `upsert` uses an `onConflict` that includes `tenant_id`, so a conflict can never update another tenant's row. Every unscoped `db.from(...)` is one of the documented cross-tenant lookups: `channels.findTenantByExternalId`/`findByWebhookId` (filtered by status `connected`; the webhook id is a unique uuid), `retention.tenantIds`/`findMetaDeletionTargets`/`metaDeletionReceived` (LIKE escaped), `tenants.get/ensure/listAll`, `platformAdmins`, `users.count/get`, and `usage.remaining`'s cap read. The callers are the Meta and Telegram webhooks (signed / secret), the retention CLI, the Meta deletion callback (HMAC) and `/platform` (gated). The non-uuid tenant id check fails loudly.
- **Schema.** Composite FKs `(tenant_id, id)` make cross-tenant references impossible, which `rls_cross_tenant.sql` tests. The column-scoped UPDATE grants never include `tenant_id`. `tenant_secrets`, `rate_limits`, `login_attempts` and the limiter tables have no browser grants. RLS is on for every table, and anon has nothing. The partial unique index `uq_channel_external` stops two tenants from connecting the same bot, page or number.
- **RPCs.** All are `SECURITY DEFINER` with `search_path = ''` and fully qualified names. The server RPCs (`rate_limit_hit`, `usage_add`, `conversation_touch`, `retention_*`, `platform_tenant_overview`) have EXECUTE revoked from public, anon and authenticated, and granted only to `service_role`. `platform_tenant_overview` is read-only, clamps limit and offset, and escapes LIKE wildcards. `app_private` is not an exposed schema.
- **Invitations.** The token is 32 random bytes (`invite-token.ts`); only its SHA-256 is stored. It expires after 7 days and is single-use (`accepted_at`, `FOR UPDATE`). It is **bound to the JWT email** and its role is limited to admin/agent, so it can never grant owner. The service role is used only after the caller proved admin with their own RLS-scoped session. Earlier pending invites are revoked. Accepting is a POST server action, never a GET side effect.
- **create_tenant.** The caller becomes owner, with a limit of 5 owned tenants. Plan, status and cap are not tenant-editable (no grants). Team changes run through the user-session client and RLS (`role <> 'owner'`; no promotion to owner, which is tested). The app blocks self-demotion.
- **Sessions.** `getClaims()` verifies the JWT. Memberships are read through RLS on every request. The `active_tenant` cookie is only a hint and is re-validated against memberships (`pickActiveTenant`, `setActiveTenant`). Auth cookies are httpOnly, SameSite=Lax, and Secure on https or production. The proxy only refreshes the session; every page, action and route re-checks. A removed member loses access on their next request.
- **Role checks.** `requireRole("admin")` or `assertRole` guards every admin mutation: tone, context (4 actions), sources (3), the `section-file` and `sources/upload` routes, channels (connect, disconnect, Telegram connect, re-register, disconnect), Shopify connect/manual/demo/disconnect (`tenantOr401("admin")`), brand save (`hasRole` in the route and again in `saveBrand`), and team (4 actions). Agent-level routes (inbox reply/status/simulate, `shopify/test`) are intentional and rate-limited where they act as an oracle. Every cookie-authenticated state-changing route handler calls `checkSameOrigin`; server actions get Next's Origin check.
- **Open redirect.** `safeNext` allows only relative paths and rejects `//`, backslash and control characters, then re-parses against a fixed origin. It is used for `next` and `auth_next` in login, signup and confirm. Signup, sign-in and forgot-password return generic results (no user enumeration).
- **Storage.** Every object path is built by `objectPath(tenantFolder, safeKey)`, and every persisted path is read back through `keyFromStored`, which returns null for another tenant's prefix. `sources.create` refuses a foreign prefix. The local `/api/brand-assets` route accepts only `^[A-Za-z0-9_-]` tenants and `logo-<uuid>.(png|jpg|webp)` names, and sends `nosniff` and `CSP default-src 'none'`. Logos are checked by magic bytes **and** declared type, SVG is rejected, and keys are random per upload. The `brand-assets` bucket allows only png/jpeg/webp and is not listable (no SELECT policy).
- **Branding.** Colours must match `^#[0-9A-F]{6}$` (zod plus a DB CHECK), and the font is an enum. Inline CSS variables carry only computed hex values and a fixed font stack, so no CSS injection is possible. `logoPath` never comes from the client.
- **Telegram.** Each bot has its own random webhook uuid plus a 256-bit `secret_token`, stored AES-GCM-encrypted with the bot token and compared in constant time over SHA-256 digests. The webhook fails closed (unknown id, disconnected, missing or wrong secret = 401), caps the body at 1 MB, accepts private chats only and drops bot or `sender_chat` messages. Sends are plain text (no `parse_mode`). The token is masked in the UI (`maskTelegramToken`) and never logged or put in audit rows. The secret rotates on re-register, and switching bots calls `deleteWebhook` on the old one. `getMe` proves possession of the token. The webhook URL comes from env `PUBLIC_URL` only (no request-derived SSRF).
- **AI.** The key is only in a request header and never logged; only status and error class are logged. Customer text goes through `redactPII`/`redactForLLM`, and order-flow bot replies are excluded from history. A refusal leads to handoff. Output is capped at 400 tokens and validated. Usage is metered per tenant, the simulator included, and the cap fails closed.
- **Platform admin.** `requirePlatformAdmin` runs in both the layout and the page and returns 404 otherwise. In Supabase mode it uses the `platform_admins` table only; `PLATFORM_ADMIN_EMAILS` is SQLite-only. `listAll` runs only after the check (tested), and views are audited once per hour. The screen shows counts only.
- **Public pages.** The marketing and legal pages are `noindex` (`lib/platform/seo.ts`).
- **Retention in Supabase mode.** Purge and per-customer delete are single-transaction RPCs, scoped by tenant. The Meta deletion callback verifies the HMAC and audits the code only.
- **Dependencies.** `npm audit` reports 0 vulnerabilities (525 packages). Next 16.4.6.
- **Git history.** No real secrets. Pattern hits are test fixtures (`sb_secret_must_not_leak…`, `sb_secret_offline_test`, `123456789:AAHfake…`) and the `setup.mjs` template. Only `.env.example` is tracked, and the CI secret scan is present.
- **Logging.** No message bodies, emails, tokens or URLs with tokens are logged. DB errors are mapped to code and constraint only.

## Repro notes

- **H1**: the scratch test is in the session scratchpad, not the repo. Equivalent steps by hand (SQLite): `getOrCreate(t,"messenger","psid-1")` → `messages.add(in)` → `setStatus(id,"needs_human","safety")` → POST `/api/inbox/conversations/<id>/status {"action":"resolve"}` → `npm run purge` with the clock 91+ days later. The conversation and its messages are gone. Expected: kept, with bodies masked after 365 days.
- **M1(a)**: as an agent with a valid access token and the publishable key, send `curl -X PATCH "$URL/rest/v1/conversations?id=eq.<id>" -H "apikey: $PUB" -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" -d '{"escalation_reason":null}'`. - **M3**: per account, 5× `create_tenant`, then for each tenant loop `POST /api/inbox/simulate` ×20 → `DELETE /api/inbox/simulate`. Watch `ai_usage` climb to 2M per tenant.
